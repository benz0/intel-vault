# Account structure

## Layout

```
{vault}/
├── _Portfolio/
│   ├── Renewal Calendar.md
│   ├── Risk Board.md
│   └── Internal People.md
└── Accounts/
    └── {Account}/
        ├── Current State.md                dated status blocks, newest first
        ├── Account Overview.md
        ├── Customer Intelligence Dashboard.md
        ├── Meeting Log.md
        ├── Action Tracker.md
        ├── Sources/                        read-only
        ├── _Prep/
        ├── _derived/                       spreadsheet caches, never hand-edited
        ├── Meetings/                       only for genuinely cross-product meetings
        ├── Stakeholders/
        │   ├── Stakeholder Index.md
        │   ├── Customer/
        │   └── Internal/
        └── {Product}/
            ├── {Account} {Product}.md      folder note
            ├── MEDDPICC.md
            ├── Account Plan.md
            ├── Success Plan.md
            ├── Architecture.md
            ├── Products and Use Cases.md
            ├── Risks and Opportunities.md
            └── Meetings/
```

Templates for each file are in `_system/packs/cse/templates/account-files.md`.

**One folder per product relationship.** If an account owns two products, they get separate folders with separate MEDDPICC, plans, and risks. Product motions are distinct.

**Product folders use the full product name** (`Vault Enterprise`, not `Vault`).

## Account Overview frontmatter (drives the portfolio views)

```yaml
---
type: account
account:
industry:
products: []
renewal_date:          # YYYY-MM-DD, the nearest one
acv:                   # number, no currency symbol or commas
sentiment:             # red | yellow | green
risk_status: []        # any of: technical, consumption, commercial. Empty means none.
primary_risk:          # which one is most likely to cost the renewal
program:               # none, or the name of an escalation program the account is in
last_updated:
---
```

These fields let `Renewal Calendar.md` and `Risk Board.md` be live queries (for example Obsidian Bases) instead of files regenerated by reading every account.

## One product, several commercial relationships

An account can hold several commercial relationships under one product, each with its own ACV, renewal date, and sentiment. **`Account Overview.md` holds one of each and cannot represent that.** So split what is commercial and share what is technical:

```
{Product}/
  {Account} {Product}.md             folder note, links each relationship
  Architecture.md                    shared, one deployment reality
  Products and Use Cases.md          shared
  {Relationship A}/
    {Account} {Product} {Relationship A}.md   relationship note, commercial frontmatter
    MEDDPICC.md
    Success Plan.md
    Risks and Opportunities.md
  {Relationship B}/
    ...
```

Relationship note frontmatter: `type: product-index`, `account`, `product`, `relationship`, `acv`, `renewal_date`, `sentiment`, `risk_status`, `last_updated`. Portfolio views query `type: product-index` so every renewal gets its own row.

**Only split when the relationships genuinely differ commercially.** If the owner already keeps separate success plans or platform records for them, mirror that.

## Folder notes

A link to a folder resolves to nothing. Each product folder gets a short landing note named with the account prefix so it stays unique: `Accounts/Acme/Vault Enterprise/Acme Vault Enterprise.md`, linked as `[[Acme Vault Enterprise|Vault Enterprise]]`. Frontmatter `type: product-index`, two or three sentences, links to the files beneath. It must not restate their content.

## Where a meeting file goes

Most specific wins:

1. `{Product}/{Relationship}/Meetings/` when the content is specific to one commercial relationship
2. `{Product}/Meetings/` when it spans relationships within one product
3. `Accounts/{Account}/Meetings/` only when it genuinely spans products

**Never duplicate a meeting file across folders.** File it once and link to it.

## Stakeholder files

**Do not create a file for someone who appeared once with no established role.** List them in `Stakeholder Index.md` under "Seen once, role unknown" with the date and meeting.

**Authority overrides that threshold.** Anyone whose approval, budget, or veto can move the relationship gets a file even on thin evidence, tagged `[Coverage: thin, expand when more is known]`.

Always identify, explicitly: **champions, economic buyers, competitors' advocates, executive sponsors.**

## Intake additions for accounts

When `intake` runs on an account, add these rows to CHANGES DETECTED:

```
MEDDPICC movement:       ...
Architecture changes:    ...
Platform updates owed:   ...
```

and propagate to `MEDDPICC.md`, `Risks and Opportunities.md`, `Architecture.md`, `Action Tracker.md`, and `Account Overview.md` if the top-level picture moved. Then ask whether to run `cs-update` and say whether the meeting changes sentiment, health, or an open risk record.

## Brief additions

The `brief` workflow adds these sections for this pack:

- **Renewals inside 120 days:** Account, Product, Date, ACV, Risk posture, Plan credible Y/N
- **Platform debt:** what happened in the vault that is not in `cs_platform` yet, by cadence rule

## Prep additions for QBRs

- Consumption trend and what it says about adoption
- Use cases delivered vs. use cases originally sold
- Value story with actual numbers, not adjectives
- Roadmap items relevant to the customer's stated priorities
- An executive takeaway paragraph written for the customer's executive
